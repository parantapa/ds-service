# How to build the ds-service server

The server is a single C++23 binary, `ds-service`.
The same build produces the C++ client libraries,
and, when asked, the Python client's extension module.
[Conan](https://conan.io/) manages the dependencies.
CMake drives the build.

## Requirements

- `build-essential` (or another C++23 toolchain, `g++` 14 or later), `cmake` (>= 3.31), `git`
- [Conan](https://conan.io/) 2.x on `PATH` (`pip install conan`).
    All the C++ dependencies come from Conan.

The first Conan run builds the missing dependencies from source,
and takes far longer than a later build.
Subsequent builds reuse the Conan cache.

## Build the server

From the repository root:

```sh
conan install . --build=missing
. build/Release/generators/conanbuild.sh
cmake -S . -B build/Release \
    -DCMAKE_BUILD_TYPE=Release \
    -DCMAKE_TOOLCHAIN_FILE=generators/conan_toolchain.cmake
cmake --build build/Release --parallel
```

Source `conanbuild.sh` in the same shell as the `cmake` calls.
It sets up the environment of the Conan-provided build tools,
such as `protoc` and `grpc_cpp_plugin`.

The build writes the binary to `build/Release/ds-service`.
For a debug build,
pass `-s build_type=Debug` to `conan install`.
Then use `-DCMAKE_BUILD_TYPE=Debug` with a matching `build/Debug` directory.

### After changing the proto

The build regenerates the C++ stubs from `cpp/grpc/ds-service.proto`.
Run the build commands again.
Nothing else is generated by hand.
The proto is only the gRPC encoding of the plain types
in `cpp/common/include/ds-service/`.
See the [developer notes](../developer-notes.md#a-new-operation-touches-every-layer)
for the other layers that a new or changed operation touches.

## Choose what to build

Three CMake options select the parts:

| Option | Default | Builds |
| --- | --- | --- |
| `DS_SERVICE_BUILD_SERVER` | `ON` | The `ds-service` binary. |
| `DS_SERVICE_BUILD_CLIENT` | `ON` | The C++ client libraries. See the [C++ client reference](../reference/cpp-client.md). |
| `DS_SERVICE_BUILD_PYTHON` | `OFF` | The Python client's extension module, `ds_service_client._ext`. Needs `DS_SERVICE_BUILD_CLIENT`. |

Pass them to the `cmake -S` call, for example `-DDS_SERVICE_BUILD_CLIENT=OFF`.
The matching Conan options, `with_server`, `with_client` and `with_python`,
set the same defaults when you pass them to `conan install` with `-o "&:with_server=False"`.
A build without the server does not need
`spdlog`, `argparse`, `parallel-hashmap` or `re2`.

A C++ program that uses the client links the CMake target `ds-service-connect`.

## Build the Python module

The Python module needs [nanobind](https://nanobind.readthedocs.io/)
in the Python that CMake finds,
and Python 3.12 or later with its development headers:

```sh
pip install nanobind
cmake -S . -B build/Release \
    -DCMAKE_BUILD_TYPE=Release \
    -DCMAKE_TOOLCHAIN_FILE=generators/conan_toolchain.cmake \
    -DDS_SERVICE_BUILD_PYTHON=ON
cmake --build build/Release --parallel
```

To choose the Python, add `-DPython_EXECUTABLE=/path/to/python`.

The build copies the module and its type stub into `python/ds_service_client/`,
so the test suite and pyright find them in the source tree.
`-DDS_SERVICE_PYTHON_INPLACE=OFF` turns the copy off.

To build the wheel instead, run `pip wheel .` from the repository root.
It needs no Conan install beforehand:
pip installs Conan for the build,
and `cmake/conan-install.cmake` runs `conan install` itself.
It does need a C++23 toolchain.
A wheel built this way is tagged for this machine only.
The wheel to publish comes from `cibuildwheel`,
which builds it in a manylinux container and needs docker or podman.

## Run the tests

A build with both the server and the client
has a C++ smoke test of the client against the server:

```sh
ctest --test-dir build/Release --output-on-failure
```

The Python suite needs the Python module.
See the [developer notes](../developer-notes.md#building-running-and-testing).

## Install the binary

```sh
cmake --install build/Release --prefix /path/to/prefix
```

This installs the `ds-service` binary under `/path/to/prefix/bin`.
It installs neither the client libraries nor their headers.

## Run the server

```sh
ds-service --address 0.0.0.0:5051
```

The default address is `127.0.0.1:5051`.
Run `ds-service --help` for the full argument list.

## Static musl binary

`scripts/Dockerfile` builds `ds-service` against musl on Alpine 3.24,
and links it statically:

```sh
docker build -f scripts/Dockerfile -t ds-service:static .
docker run --rm -p 5051:5051 ds-service:static
```

The final stage is `FROM scratch`,
so the image holds nothing but the binary.
To extract that binary instead of running it:

```sh
docker build -f scripts/Dockerfile --output type=local,dest=./dist .
```

ConanCenter has no musl binaries.
The first build compiles the whole dependency tree from source.
It takes longer than the normal build.

The Conan profile and linker flags used here differ from the normal build.
See [about the static musl build](../explanation/the-static-musl-build.md)
for the differences, and for the reason the build needs them.
